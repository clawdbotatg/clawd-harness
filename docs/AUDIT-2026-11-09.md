# Whole-project audit — 2026-11-09

One pass over the entire repo (server, UI, fleet, PM, tools, tests, docs) by
seven read-only auditors, each reading its slice line by line. This file is
the full result: what was fixed that day, and everything still open with how
to fix it.

**How to read the open items**

- **Confidence** is the auditor's: `SURE` = every caller/usage was read,
  `LIKELY` = the mechanism is clear from the code but the symptom was not
  observed, `UNSURE` = worth a look. Items marked **✔ re-checked** were also
  confirmed by hand against the code. Everything else is from reading only —
  reproduce before fixing.
- **Line numbers are from before the audit's own commits** and have drifted by
  a few lines. Function names are the reliable anchor.
- **Cost** flags fixes that restart things: a `server.py` change restarts and
  resumes every session on every box; a worker change restarts every worker
  (may cost passkeys); any `fleet/*.py` change restarts the relay.

## 3. Server (`server.py`) — open

### S1. A dead login quarantines its whole org — ✅ FIXED (batch 2)
Only a real limit wall (429 / measured 100%) quarantines the org now; a refused
or expired login is marked broken alone. `test_wall_quarantine.py` covers it
(the new cases fail on the old code). Original finding:

`rescue_bounced_prompt` (~7839–7868). When the evidence is `AUTH_FAIL` or
`login_gone`, it still calls `_mark_pool_walled(acct, "session")`, which stamps
`walled_until` on every account in that org. `_candidates` and
`_blind_alternative` filter on `walled_until`, so the same-org sibling the
comments say to move to is excluded, and new spawns avoid a healthy org for up
to 5 h. On the `AUTH_FAIL` path `acct.broken` is never set (unlike
`maybe_handoff`).

**Fix:** split on the evidence. Pool wall (pct ≥ 100 or `RATE_LIMITED`) →
`_mark_pool_walled` as today. `AUTH_FAIL` / `login_gone` → mark only that
login broken, leave the org routable. Add a case to
`test_wall_quarantine.py`: dead login + healthy sibling in the same org → the
sibling is chosen. Read `EXPECTATIONS.md` first; this is the contract file.

### S2. Two background loops have no error fence — ✅ FIXED (batch 2)
Both ticks are wrapped (`_poll_accounts_tick`, `_loop_crashed`); a repeating
traceback is logged at most once a minute. Original finding:

`watch_ui` (~11004) and `poll_accounts_loop` (~7396). One exception ends the
thread for the life of the process. Losing `watch_ui` stops project reconcile,
the background-work sweep, browser reload **and the restart gate (deploys)**.
Losing the poller stops usage polling, auto-switch and the handoff sweep. The
poller reaches `fresh.start()` (PTY/Popen), and Errno 24 is a known condition
here.

**Fix:** wrap each loop body in `try/except Exception`, log with traceback,
`continue`. Move each body into a `_tick()` helper so the diff is not a
100-line re-indent. `auto_update_loop` and `_boot_stagger` already show the
pattern.

### S3. 🔍 check may refuse codex sessions — ✅ FIXED (batch 7)
`_has_conversation()` (~5164) greps for claude's `"type":"user"` /
`"type":"assistant"`. Codex rollouts are `response_item` payloads, so "claude
checks codex" answers "nothing to check yet" on older codex and works on
0.167 only by accident. `test_check.py` stubs the method.

**Fix:** decide with `self._slim_event(line)` returning role user/assistant
(engine-aware already), or add an `Engine.has_conversation` hook. Add an
un-stubbed test with a small codex rollout fixture.

### S4. A respawn re-streams the whole transcript as live — ✅ FIXED (batch 7)
`_tail_transcript` (~5207). No seek on attach, so after a handoff/rescue (or a
subscribe to a boot-parked session) every old line goes to current viewers
without `history: True`; `_replay_history` then sends the last 150 again. The
UI has no dedupe and passes live assistant text to `speak()`.

**Fix:** on the first attach of a `resuming` start, seek to EOF (history is
already served by `_replay_history`); or tag those lines `history: True`.
Verify with a sandboxed session: resume, count frames per subscriber.

### S5. Send to a boot-parked session types too early; concurrent sends can drop one — ✅ FIXED (batch 7)
`send_message` (~4796) calls `ensure_started()` then writes immediately, where
every other respawn-then-type path waits (`wait_ready`). And `ensure_started`
(~4243) clears `starting` under the lock but runs `start()` outside it, so a
second caller proceeds, finds `master_fd is None` and drops its text silently.

**Fix:** hold a `_start_lock` across `start()`, and
`if self.ensure_started(): self.wait_ready(...)` before the write.

### S6. Transcript is re-read whole, constantly — ✅ FIXED (batch 8)
- every `subscribe` (each tab switch) reads and parses the entire transcript,
  twice when the ring is shallow (`_history_seed_bytes`, `_replay_history`);
  `tail_events` does the same and is retried in a 5 s loop;
- every Stop reads the whole transcript to keep ≤ 7k characters
  (`_regenerate_digest` etc.), even when naming is unconfigured.

**Fix:** one shared tail-bytes reader (the bounded window `_search_transcript`
already uses), parse once per subscribe; in the naming path return early when
`BANKR_API_KEY` / `BANKR_BASE_URL` are unset and read only head + tail bytes.

### S7. Every hook does a full sessions + projects rebuild — ✅ FIXED (batch 8)
`broadcast_sessions()` on every PreToolUse/PostToolUse builds `meta()` for all
sessions and calls `broadcast_projects()` (one locked pass over all sessions
per project, then a `json.dumps` of the list to compare). A UserPromptSubmit
also saves the registry twice.

**Fix:** skip `broadcast_sessions` for tool hooks when status is unchanged
(the `hook` frame already carries busy/waiting/tool); count sessions per
project in one pass; drop one of the two saves.

### P1. Pipeline step output is capped at 700 characters — ✅ FIXED (batch 5)
`_step_output` reads `world.session_detail()`, which truncates `last_answer`
to 700 (400 on the transcript fallback). `STEP_OUTPUT_CHARS=4000` and friends
are unreachable, so hand-offs between steps and the final report are cut.

**Fix:** read `c.state()["last_answer"].get(cid)` directly; pass `chars=2000`
on the fallback. Add a long-answer case to `test_pipeline.py`.

### P2. Pipeline defaults apply to step 1 only; a step that fails to start wedges the chain — ✅ FIXED (batch 5)
`start_pipeline(machine=, pid=)` mutates a deep copy; `_advance` runs step 2
with no defaults → "no machine None". And a step ≥ 2 that fails to start stays
`pending`: `advance_pipeline` says "no running step", `start_pipeline` says
"already started".

**Fix:** persist the defaults onto the task as a ledger event and read them in
`_run_step`; in `_advance`, when nothing is running but a pending step exists,
run it. Tests: a pipeline with the machine only at start; a step-2 spawn
failure followed by `advance_pipeline`.

### P3. Telegram bypasses the turn lock — ✅ FIXED (batch 5)
The bridge takes the shared lock itself (taking it inside `Router` would
deadlock the HTTP path, which already holds it). Original finding:

HTTP takes `chat_lock`, the autopilot takes `turn_lock`, `TelegramBridge`
calls `router.chat_stream` / `router.reset` bare. A Telegram turn can
interleave with another and repoint the shared conversation mid-flight.

**Fix:** take `turn_lock` inside `Router.chat_stream` and `Router.reset`, so
every caller is covered.

### P4. Refusals look like success — SURE
`wrap`, `check`, `external_project` return `ok: True` when the socket write
succeeded; the server's `error` frame is dropped by both clients.

**Fix:** have `HarnessClient` / `RelayMachine` keep the last `error` frame per
cid, and let these verbs wait ~1–2 s for one before answering. Update the MCP
descriptions and the persona in the same change (the three-places rule).
